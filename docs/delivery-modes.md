# Delivery Modes

Gargantua runs the same engine two ways. Choosing between them is a packaging decision,
not a capability trade-off: routing, memory, guardrails, HITL, RAG, streaming, cost
tracking and A2A behave identically in both.

| | **Library mode** | **Runtime mode** |
|---|---|---|
| Who writes the agent | A developer, in Java | The Studio, declaratively |
| Where it runs | Inside your Spring Boot application | A generic runtime container image |
| Tools come from | Compiled `@AgentTool` methods | MCP servers named in the manifest |
| Skills come from | Your classpath or filesystem | The bundle's `skills/` directory |
| Configuration | `application.yml` | `manifest.yaml` (plus environment) |
| Deployable artifact | Your application JAR or image | A signed, versioned `.gbundle` |
| Add a tool by | Writing a Java method and redeploying | Pointing at an MCP server; no rebuild |

Both modes are first-class and neither is deprecated. If you are using Gargantua today as
a Maven dependency, nothing about that has changed — see [Library mode](#library-mode).

---

## Library mode

**Gargantua is a dependency. Your application is the agent.**

This is the original model and remains fully supported. Add `agent-engine`, annotate some
methods, drop in a `SKILL.md`, and run your own Spring Boot application.

```xml
<dependency>
    <groupId>com.github.giskardb.gargantua</groupId>
    <artifactId>agent-engine</artifactId>
    <version>${gargantua.version}</version>
</dependency>
```

```java
@Component
public class OrderTool {

    @AgentTool(description = "Retrieves order status by order ID")
    public OrderStatus getOrderStatus(String orderId) {
        return orderService.getStatus(orderId);   // your code, your classpath, your beans
    }
}
```

Everything you already know keeps working: `@AgentTool`, `@ToolRetry`, `@RequiresApproval`,
`@CacheableToolResult`, `@AgentSkill`, `@AgentsFlow`, custom guardrails as `@Component` +
`@Order`, custom `@Bean` overrides of any framework component.

**Nothing was taken away.** The recent runtime work added a seam — tools now arrive through
a `ToolProvider` — but annotation scanning is simply one implementation of it
(`AnnotationToolProvider`), and it is registered for you. Your tools are discovered exactly
as before, and they take precedence over remote tools with the same name.

Library mode also gained MCP: you can now consume external MCP servers without writing any
Java for them. See [Consuming MCP servers](tools-and-annotations.md#consuming-mcp-servers).

```yaml
agent:
  mcp-client:
    servers:
      - name: github
        transport: stdio
        command: npx
        args: ["-y", "@modelcontextprotocol/server-github"]
```

**Use library mode when:**

- Your tools need to call into your own code — repositories, services, an existing domain model
- The agent is a feature of a larger application rather than a standalone service
- You want the shortest path from an idea to a running agent
- You are scaffolding with the Maven archetype

Start here: [Try it in 60 seconds](../README.md#try-it-in-60-seconds).

## Runtime mode

**Gargantua is a process. The agent is a bundle it loads.**

A generic runtime image executes a declarative bundle handed to it at startup:

```bash
docker run -v ./customer-agent.gbundle:/bundle:ro \
           -e LLM_PRIMARY_API_KEY=sk-... \
           ghcr.io/giskardb/gargantua-runtime:1.0
```

Or locally:

```bash
gargantua validate my-agent.gbundle   # parse, verify integrity, report unapplied fields
gargantua run       my-agent.gbundle
```

The bundle is a directory or archive:

```
customer-agent.gbundle
├── manifest.yaml     required — see docs/architecture/agent-manifest.md
├── metadata.json     optional — checksum, signature, provenance
├── skills/           SKILL.md folders
├── prompts/
├── schemas/
└── policies/
```

At startup the runtime loads the bundle, verifies its checksum when one is declared, and
projects the manifest onto the same `agent.*` settings the engine already binds. That is
why behaviour is identical between modes: there is one engine, configured two ways.

**Bundles contain no executable code.** That constraint is deliberate — it is what makes
signing meaningful and what allows a bundle to be distributed and promoted unchanged. Tools
therefore come from MCP servers declared in the manifest. See
[ADR-003](architecture/runtime-decisions.md#adr-003--bundles-are-declarative-and-contain-no-executable-code).

**Use runtime mode when:**

- Agents are authored by non-developers, or generated by the Studio
- You want to ship a new agent version without a build pipeline
- You need immutable, signed, independently versioned agent artifacts
- You are running many agents and want one image to maintain

## The image and the bundle version independently

The runtime image is the executor; the bundle is the payload. They are separate artifacts:

```
gargantua-runtime:1.0        + customer-agent.gbundle v1.2   → running agent
gargantua-runtime:1.1        + customer-agent.gbundle v1.2   → patched engine, same agent
gargantua-runtime:1.0        + customer-agent.gbundle v1.3   → new agent, same engine
```

Roll a bundle forward without rebuilding the image; patch the image without republishing
bundles. A manifest may pin the image it needs:

```yaml
spec:
  runtime:
    image: ghcr.io/giskardb/gargantua-runtime:1.0
```

## When you need Java tools in runtime mode

Build a custom runtime image using library mode, then name it in the manifest. This is the
supported path, and it is a build-time operation — there is no dynamic class loading.

```java
@SpringBootApplication
public class AcmeRuntime {
    public static void main(String[] args) {
        GargantuaRuntime.main(args);   // same entry point, your beans on the classpath
    }
}
```

```dockerfile
FROM ghcr.io/giskardb/gargantua-runtime:1.0
COPY target/acme-runtime.jar /app/runtime.jar
```

```yaml
spec:
  runtime:
    image: acme/gargantua-runtime:2.1   # bundles targeting this image get the extra tools
```

The compiled tools are discovered by the same annotation scanning as in library mode, and
they coexist with the MCP tools the bundle declares.

## Configuration precedence

Both modes end up binding the same `agent.*` properties. In runtime mode the manifest is
inserted as a property source just below the process environment:

```
command line  >  environment variables  >  bundle manifest  >  application.yml defaults
```

So a bundle overrides the image's defaults, while an operator can still override the bundle
in an emergency without republishing the artifact. Secrets are never in the bundle — a
manifest references them by name and the runtime resolves them:

```yaml
env:
  GITHUB_TOKEN: ${secrets.github-token}
```

See [ADR-005](architecture/runtime-decisions.md#adr-005--secrets-are-referenced-by-name-never-embedded)
and the `SecretResolver` extension point in [Extending](extending.md).

## Choosing

| If you… | Use |
|---|---|
| Are evaluating Gargantua for the first time | Library mode, via the archetype |
| Need tools that call your own services | Library mode |
| Are embedding an agent in an existing app | Library mode |
| Want agents authored without a build pipeline | Runtime mode |
| Need signed, immutable agent artifacts | Runtime mode |
| Run many agents on shared infrastructure | Runtime mode |
| Need both bespoke Java tools and bundle distribution | Runtime mode with a custom image |
