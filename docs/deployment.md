# Deployment

## Publishing the Framework (for maintainers)

### CI Pipeline

Every push to `main` or PR triggers the CI workflow (`.github/workflows/ci.yml`):
- Builds all modules on Java 21 and Java 25
- Runs unit tests
- Verifies `agent-core` has zero Spring dependencies
- Verifies no `javax.*` imports exist

### Release to GitHub Packages

Create a version tag to trigger the release workflow (`.github/workflows/release.yml`):

```bash
git tag vX.Y.Z          # e.g. v1.1.2
git push origin vX.Y.Z
```

This will:
1. Build and test all modules
2. Publish JARs to GitHub Packages (`https://maven.pkg.github.com/giskardb/gargantua`)
3. Create a GitHub Release with changelog

**Manual release** (with optional version override):
- Go to Actions → Release → Run workflow
- Optionally set a version and/or dry-run mode

### Consuming the Framework

**Via JitPack (recommended — no auth needed):**

```xml
<repositories>
    <repository>
        <id>jitpack.io</id>
        <url>https://jitpack.io</url>
    </repository>
</repositories>

<dependency>
    <groupId>com.github.giskardb.gargantua</groupId>
    <artifactId>agent-engine</artifactId>
    <version>v1.2.2</version>
</dependency>
```

JitPack builds directly from Git tags. No `settings.xml`, no tokens.
Projects generated by the archetype already have this configured.

See the [Repository setup section in README](../README.md#repository-setup--jitpack) for full details including GitHub Packages as an alternative.

## Which mode are you deploying?

Gargantua deploys two ways. Everything below the Kubernetes section applies to both; the
container image and its inputs differ.

| | Library mode | Runtime mode |
|---|---|---|
| Image | Built from **your** application | `gargantua-runtime`, generic |
| Configuration | Baked-in `application.yml` + env | Mounted bundle + env |
| Redeploy to change the agent | Rebuild and push your image | Swap the bundle |

See [Delivery Modes](delivery-modes.md) for how to choose.

## Runtime mode — the bundle-executing image

The runtime image is the executor; the bundle is the payload. Build it from the repository
root (the Dockerfile needs the whole reactor):

```bash
docker build -f agent-runtime/Dockerfile -t gargantua-runtime:1.0 .
```

Run it with a bundle mounted read-only:

```bash
docker run -p 8080:8080 \
  -v ./customer-agent.gbundle:/bundle:ro \
  -e LLM_PRIMARY_API_KEY=sk-... \
  gargantua-runtime:1.0
```

The image is non-root, exposes 8080, and has a `HEALTHCHECK` against
`/actuator/health/readiness`. It is built on `eclipse-temurin:21-jre-jammy` rather than
Alpine because semantic routing loads ONNX Runtime, whose native library needs glibc.

### Bundle location

Resolved in this order:

1. positional argument — `java -jar runtime.jar run /path/to/bundle`
2. `--bundle=/path/to/bundle`
3. `GARGANTUA_BUNDLE` environment variable (the image sets `/bundle`)
4. `/bundle`

### Commands

```bash
java -jar runtime.jar run       [bundle]   # execute (the image's default CMD)
java -jar runtime.jar validate   bundle    # parse, verify integrity, report gaps
java -jar runtime.jar help
```

`validate` exits `0` on success, `1` on an invalid bundle, `2` on a usage error — usable as
a CI gate before publishing.

### Configuration precedence

```
command line  >  environment variables  >  bundle manifest  >  image application.yml
```

A bundle overrides the image's defaults; an operator can still override the bundle without
republishing it. Secrets are never in the bundle — the manifest references them by name and
the runtime resolves them from the environment. See
[ADR-005](architecture/runtime-decisions.md#adr-005--secrets-are-referenced-by-name-never-embedded).

### What to check at startup

Two log lines matter on every deploy:

- **Integrity.** If `metadata.json` declares a checksum, a mismatch refuses to start. An
  unsigned bundle logs a warning and proceeds.
- **Unapplied fields.** Manifest declarations the runtime accepts but does not enforce
  (`spec.memoryLayers`, `spec.allowedRoles`, `spec.runtime.minVersion`) are logged as
  warnings. Do not assume a declared constraint is in force — see the
  [enforcement status table](architecture/agent-manifest.md#enforcement-status).

### MCP servers in production

`agent.mcp-client.servers` with `transport: stdio` launches **child processes** inside the
container, so the image must contain that runtime (for example Node for `npx`-based
servers). Remote `http`/`sse` servers avoid this. By default an unreachable server is
logged and skipped so the agent still starts; set `fail-fast: true` when a server is
essential enough that starting without it would be worse.

### Kubernetes

The manifests in `k8s/` currently target library mode — `k8s/base/deployment.yaml` pins an
application image and mounts no bundle. For runtime mode, change the image and add the
bundle as a volume, for example a read-only `ConfigMap`, an `initContainer` that pulls it
from the Registry, or a persistent volume.

## Local Development — Docker Compose

The framework repo does not ship a root-level `docker-compose.yml` — Docker Compose lives **inside the agent project generated from the archetype**. Once you have generated `my-agent`:

```bash
cd my-agent

# Build and run the app + dependencies
docker compose up

# Infrastructure only (run the app from your IDE)
docker compose up mongo redis ollama
```

The generated compose defines four services: `app` (your agent), `mongo` (8.0), `redis` (7.4-alpine), `ollama` (latest, with the routing model volume).

## Dockerfile (library mode)

The **archetype-generated** `Dockerfile` — for an application that embeds the engine — is a two-stage build. For the runtime-mode image see [above](#runtime-mode--the-bundle-executing-image).

| Stage | Base Image | Size | Startup |
|-------|-----------|------|---------|
| `builder` | maven:3.9-eclipse-temurin-21-alpine | — | (build only) |
| runtime | eclipse-temurin:21-jre-jammy | ~300MB | ~3-5s |

> **Why `jammy`, not `alpine`?** The semantic routing path pulls in ONNX Runtime via `langchain4j-embeddings`, whose native `libonnxruntime.so` depends on `libstdc++.so.6` — not available on Alpine/musl. Ubuntu Jammy ships glibc.

```bash
# From inside your generated agent project
docker build -t my-agent:latest .
```

```bash
./mvnw clean package -Pnative -DskipTests
```
The `native` profile is included by default in archetype-generated projects. See [gargantua-examples](https://github.com/GiskardB/gargantua-examples) for working examples.

🚧 **Planned — not yet wired.** A `GargantuaRuntimeHints` class to register reflection hints for records and resource patterns for skills is on the roadmap. Until it lands, you must register your own hints in your application:

```java

```

### Key Components
- **Deployment** — non-root container, topology spread constraints, graceful shutdown (30s for SSE)
- **Service** — ClusterIP 80→8080
- **HPA** — CPU/memory fallback autoscaler
- **KEDA ScaledObject** — scales on Prometheus query `sum(rate(http_server_requests_seconds_count{app="gargantua-parent"}[2m]))` (HTTP request rate, not SSE-specific — see `k8s/base/keda-scaledobject.yaml`)
- **PDB** — minAvailable: 1 during disruptions
- **ServiceMonitor** — Prometheus scraping at /actuator/prometheus

### Ingress for SSE

> No Ingress manifest ships in `k8s/` — bring your own. If you front the agent with NGINX,
> these annotations are required or streaming responses will be buffered and arrive in one
> chunk at the end:

```yaml
nginx.ingress.kubernetes.io/proxy-read-timeout: "60"
nginx.ingress.kubernetes.io/proxy-buffering: "off"
```

### Why Pods Are Stateless
All state is in Redis (working memory, HITL, tool cache) and MongoDB (episodic, knowledge, history, costs, audit trail). No session affinity needed.

### Audit Trail for Compliance
The audit trail (`AGENT_AUDIT_ENABLED=true` by default) writes an immutable `AuditEvent` for every agent decision to the `audit_trail` MongoDB collection. This append-only log captures input, routing, guardrails, tools, output, tokens, cost, and duration -- suitable for SOC 2 and GDPR compliance requirements. Set `agent.audit.retention-days` to control retention (default 365; there is no environment variable bound to it). Query audit events via `GET /api/admin/audit`.

### Sizing Reference
What the manifests in `k8s/` actually set:

| Env | Replicas | Autoscale range | CPU req/limit | RAM req/limit |
|-----|----------|-----------------|---------------|---------------|
| Dev | 1 | — | 100m/500m | 256Mi/512Mi |
| Staging | 2 | — | 250m/1000m | 512Mi/1Gi |
| Prod | 3 | 2-10 (HPA and KEDA) | 500m/2000m | 1Gi/2Gi |

There is no native-image overlay in the repository; GraalVM sizing would have to be
measured for your own build.

## Health Probes
- Liveness: `/actuator/health/liveness`
- Readiness: `/actuator/health/readiness`

These are the stock Spring Boot probe groups. **No custom `HealthIndicator` ships with the
framework** — LLM reachability and skill-registry state are not currently reflected in the
health endpoint. Add your own `HealthIndicator` bean if a probe needs to depend on them.

JVM metrics:

| Metric | Type | Tags |
|---|---|---|
| `agent.llm.model.latency` | Timer | `model`, `skill` |
| `agent.llm.model.error_rate` | Counter | `model` |
| `agent.llm.routing.fallback.used` | Counter | `original_model` |
| `agent.llm.routing.rule.matched` | Counter | `rule`, `model` |
| `agent.llm.routing.model.selected` | Counter | `model` |
| `agent.tool.cache.hits` / `.misses` | Counter | `tool`, `scope` |
| `agent.tool.retry.attempts` / `.exhausted` | Counter | `tool` |

> 🚧 **Not yet registered.** These are the intended remainder of the surface and do not
> exist yet: `agent.request.total`, `agent.request.duration`, `agent.llm.tokens.input/output`,
> `agent.tool.calls.total`, `agent.guardrail.blocked`, `agent.routing.decisions`,
> `agent.sse.connections.active`.

### Tracing (OpenTelemetry)
Spans: agent.guardrail.input → agent.routing → agent.memory.compose → agent.llm.call → agent.tool.* → agent.guardrail.output

Uses GenAI Semantic Conventions (gen_ai.system, gen_ai.request.model, gen_ai.usage.input_tokens, etc.)
